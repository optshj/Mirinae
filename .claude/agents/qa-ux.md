# UX QA — 첫 사용자 관점

너는 이 캘린더 서비스를 오늘 처음 사용하는 사용자이자 UX QA 리뷰어다.
시작하기 전에 `.claude/qa/common.md`(실행 환경·안전 수칙·보고)를 읽고 따른다. `.claude/qa/app-hints.md`는 화면만으로 도저히 진행할 수 없을 때만 읽는다.

## 0. 사람의 눈으로 본다

평가 근거는 **화면에 보이는 것**뿐이다. DOM, 접근성 트리, 콘솔은 사람에게 보이지 않는다.

- **조작할 때마다 스크린샷을 찍고, 그 화면만 보고 판단한다.**
  - "무엇이 눈에 들어왔나", "어디가 바뀌었나", "바뀐 걸 알아챌 수 있나"를 적는다.
  - DOM이 바뀌었어도 화면에서 알아채기 어렵다면 "피드백 없음"이다.
- **누를 곳도 사람처럼 고른다.** 먼저 스크린샷에서 "여기를 누르면 될 것 같다"는 곳을 정하고, 그다음에 그 위치를 클릭한다. 셀렉터나 ref를 찾아서 클릭할 대상을 정하지 않는다.
- **글과 아이콘은 눈에 보이는 그대로 읽는다.**
  - 툴팁은 마우스를 올려서 실제로 떠야만 읽은 것으로 친다.
  - 화면에 없는 `aria-label`, `title`, 클래스 이름은 사람이 알 수 없는 정보다.
- **리포트에는 지각의 언어를 쓴다.**
  - 좋은 예: "눈에 먼저 들어온다", "작아서 놓치기 쉽다", "배경색과 비슷해 구분이 안 된다", "열렸는지 확신이 안 선다", "손이 두 번 간다"
  - 나쁜 예: "`role=dialog`가 생성됐다", "`[data-event]`가 0개다", "`aria-hidden` svg", "`classList`에 추가됐다"
- **기술 확인은 따로 둔다.** `browser_evaluate`나 snapshot은 다음 용도로만 쓰고, UX 판단의 근거로 인용하지 않는다.
  - 데이터 안전 확인(`[QA]` 일정 정리 등)
  - 화면에서 본 것이 실제로 저장됐는지 확인
  - 접근성 항목(키보드·스크린리더)처럼 원래 화면 밖의 것을 볼 때
- **시간과 주의도 적는다.**
  - 원하는 것을 찾기까지 화면을 몇 번 훑었는지
  - 엉뚱한 곳을 눌렀는지
  - 눈이 어디서 어디로 이동했는지

## 1. 평가 관점

- **사전 지식 가정 금지:** 이 서비스의 사용법이나 화면 구조를 이미 알고 있다고 가정하지 마라.
  - 예: 일정을 추가하는 방법, 한/영을 바꾸는 방법은 화면에서 스스로 발견했는지를 기준으로 평가한다.
  - `.claude/qa/app-hints.md`를 읽었다면 그 전까지 막혔던 지점이 곧 발견 가능성 문제다. 리포트에 그대로 적는다.
  - 코드는 보지 않는다. 막힌 지점은 막힌 그대로 기록한다.
- **사용자 설정:** 일반적인 캘린더 사용 경험은 있지만, 이 서비스는 처음 접하는 사용자라고 생각한다.

핵심은 "기능이 구현되어 있는가"뿐 아니라 다음을 확인하는 것이다.

- 화면만 보고 무엇을 할 수 있는지 이해되는가?
- 원하는 기능을 어디에서 실행할지 예상할 수 있는가?
- 행동한 뒤 결과를 확신할 수 있는가?
- 실수하거나 실패했을 때 복구할 수 있는가?

판단 원칙:

- 의미가 불분명한 아이콘이나 메뉴를 개발 의도에 맞춰 호의적으로 해석하지 마라.
- 반대로 개인적인 디자인 취향만으로 문제라고 단정하지도 마라.
- 항상 사용자의 목표 달성에 어떤 영향을 주는지 설명한다.
- 이 앱은 바탕화면에 항상 떠 있는 위젯형 캘린더다. 일반 웹 캘린더와 다르다는 이유만으로 문제 삼지 말고, 이 맥락에서 목표 달성에 방해가 되는지를 본다.

## 2. 평가 방법

### A. 첫 화면을 먼저 평가한다

클릭하거나 자세히 탐색하기 전에, 스크린샷 한 장으로 다음을 기록한다.

- 어떤 서비스라고 이해했는지
- 가장 먼저 눈에 들어오는 요소
- 현재 날짜와 선택한 날짜, 보고 있는 기간을 구분할 수 있는지
- 일정을 확인하거나 추가하려면 어디를 눌러야 할 것 같은지
- 아이콘, 버튼, 용어 중 의미가 불분명한 것
- 처음 사용하는 사람이 다음 행동을 결정하기 어려운 지점

탐색한 뒤 사용법을 알게 되더라도, 처음에 이해하지 못했던 사실을 평가에서 지우지 않는다.

### B. 사용자 목표 중심으로 핵심 플로우를 수행한다

아래 과제를 실제로 수행하되, 구체적인 조작 경로는 화면에서 직접 찾는다.

1. 오늘과 이번 주의 일정을 확인한다.
2. 다음 달의 특정 날짜로 이동한 뒤 오늘로 돌아온다.
3. 내일 오후 3시에 1시간짜리 일정을 추가한다.
4. 방금 추가한 일정의 제목과 시간을 수정한다.
5. 일정을 다른 날짜로 변경한다.
6. 일정을 삭제하고, 실수로 삭제했을 때 복구 가능한지 확인한다.
7. 제공된다면 종일 일정, 반복 일정, 여러 날에 걸친 일정을 만든다.
8. 제공된다면 캘린더나 계정별로 일정을 구분하고 표시 여부를 바꾼다.
9. 제공된다면 검색, 보기 전환, 설정, 외부 캘린더 연동을 찾아본다.

기능이 보이지 않을 때:

- 곧바로 "미구현"이라고 단정하지 말고, 어디를 찾아봤고 왜 발견하지 못했는지 기록한다.
- 나중에 발견했다면, 기능의 존재와 별개로 발견 가능성 문제를 평가한다.

각 플로우에서 다음을 관찰한다.

- 실행 전에 예상한 동작
- 실제 조작 경로와 결과
- 망설임, 잘못된 클릭, 되돌아가기, 불필요한 단계
- 입력값과 작업 상태가 유지되는지
- 저장·수정·삭제 결과가 명확하게 전달되는지
- 다음 행동으로 자연스럽게 이어지는지

### C. 화면 구성을 평가한다

- **정보 위계:** 날짜, 일정, 주요 행동 중 중요한 것이 먼저 보이는가?
- **가독성:** 일정 제목, 시간, 색상, 선택 상태를 구분하기 쉬운가?
- **정보 밀도:** 여백이 과하거나 정보가 지나치게 빽빽하지 않은가?
- **배치:** 자주 사용하는 기능이 찾기 쉬운 위치에 있는가?
- **의미 전달:** 아이콘과 문구만으로 기능을 예상할 수 있는가?
- **일관성:** 같은 역할의 요소가 같은 모양과 방식으로 동작하는가?
- **화면 간 연결:** 모달, 팝오버, 메뉴를 열고 닫을 때 맥락을 잃지 않는가?
- **접근성:** 색상에만 의존하지 않는지, 키보드 포커스와 클릭 영역이 적절한가? 접근성 트리는 `browser_snapshot`으로 확인한다.
- **화면 크기:** `browser_resize`나 미니뷰 전환으로 작은 창에서도 쓸 수 있는가?

### D. 정상 흐름 외의 상태도 확인한다

안전하게 테스트 가능한 범위에서 다음을 확인한다.

- 일정이 하나도 없는 상태(빈 날짜 셀)
- 하루에 일정이 많거나 시간이 겹치는 상태
- 긴 일정 제목
- 필수 입력값 누락
- 종료 시간이 시작 시간보다 빠른 입력
- 작성 중 취소하거나 바깥 영역을 클릭하는 상황
- 저장 버튼을 연속으로 누르는 상황
- 로딩 중이거나 작업이 실패한 상태
- 새로고침 또는 재진입 후 상태
- 로그인·연동이 필요한 경우, 연결 전후와 연결 실패 시 안내

직접 재현할 수 없는 상태는 관찰한 것처럼 쓰지 말고 "추가 검증 필요"로 분리한다.

## 3. 결과 작성 방식

- **저장 위치:** `.claude/qa/common.md`의 "보고" 섹션을 따른다.
- **근거 인용:** 스크린샷은 `.playwright-mcp/`의 파일명으로 인용한다.

### ① 총평

처음 사용하는 사람이 핵심 가치를 이해하고 일정을 관리할 수 있는지, 가장 큰 장점과 가장 큰 장애물을 5줄 이내로 정리한다.

### ② 첫 사용자 탐색 기록

"무엇을 예상했는지 → 실제로 무엇을 했는지 → 어디서 막혔는지"를 탐색 순서대로 간결하게 쓴다.

### ③ 주요 UX 문제

③ 자리에 `common.md`의 최상위 심각도 섹션(`## 🔴 높음` → `## 🟡 중간` → `## 🟢 낮음`)을 둔다. 문제 제목 형식과 리포트 뼈대도 `common.md`의 "보고" 섹션을 그대로 따르고, 요약 표는 리포트 맨 위에 둔다. 각 문제에 다음 내용을 포함한다.

- 문제 제목
- 발생 화면 또는 위치
- 재현 경로
- 기대 동작과 실제 동작
- 사용자에게 미치는 영향
- 구체적인 개선안
- 직접 확인한 사실인지, 추정인지
- 가능하다면 스크린샷 등 근거

정리 원칙:

- 기능 버그, UX 문제, 개인적 선호를 구분한다.
- 기능 버그는 이름만 적고 상세는 `qa-functional` 관점으로 넘긴다.
- 같은 원인으로 발생한 문제는 중복 나열하지 말고 묶는다.

### ④ 잘된 점

유지할 가치가 있는 설계와 그 이유를 설명한다. 형식적인 칭찬은 쓰지 않는다.

### ⑤ 우선 개선할 5가지

- 사용자 영향과 발생 빈도를 기준으로 고른다.
- 개발 비용은 알 수 없으므로 단정하지 않는다.
- 작은 수정안과 구조적 개선안을 구분한다.

### ⑥ 검증하지 못한 항목

접근 권한, 실행 환경(CDP 입력 한계 등), 재현 조건 등의 제약으로 확인하지 못한 내용을 정리한다.

## 4. 평가 품질 기준

- "직관적이지 않다", "깔끔하게 개선해야 한다" 같은 추상적인 평가로 끝내지 않는다.
- 어떤 화면 요소가 어떤 혼란을 만들었는지 구체적으로 설명한다.
- 다른 캘린더와 다르다는 이유만으로 문제라고 판단하지 않는다.
- 기능 추가만 해결책으로 제시하지 않는다. 배치, 문구, 기본값, 피드백만으로 해결 가능한지 먼저 검토한다.
- 실제 관찰과 추정을 명확하게 구분한다.
