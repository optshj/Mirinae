# 기능 QA — 동작·버그 탐색

목표는 "되는가"보다 **"어디서 깨지는가"**를 찾는 것이다. 원인 추적과 수정은 하지 않는다. 코드를 읽지 않고, 대신 나중에 원인을 추적할 수 있을 만큼 재현 정보를 남긴다.
시작하기 전에 `.claude/qa/common.md`(실행 환경·안전 수칙·보고)와 `.claude/qa/app-hints.md`(조작 힌트)를 읽고 따른다.

## 1. 무엇을 테스트할지 정한다

테스트할 기능 목록은 이 문서에 없다. 기능은 계속 바뀌므로 매번 아래 순서로 직접 만든다.

1. **기능 지도:** 화면을 돌아다니며 보이는 기능을 목록으로 만든다. 헤더 버튼, 메뉴, 셀·일정 클릭, 하단 목록, 설정 안쪽까지 연다.
   - 이 목록은 리포트의 "방법" 섹션에 넣는다.
   - 지난 기능 QA 리포트(`docs/QA-*.md` 중 최신)의 목록과 비교해, 새로 생기거나 사라진 기능을 표시한다.
2. **최근 변경:** 지난 리포트 날짜 이후의 `git log --oneline --since=<날짜>`를 본다.
   - 커밋 메시지로 바뀐 기능을 알아내 **먼저** 테스트한다. 회귀가 가장 나기 쉬운 곳이다.
   - 커밋 메시지만 본다. diff나 코드는 열지 않는다.
   - 지난 리포트가 없으면 최근 커밋 20개를 본다.
3. **우선순위:** 최근 변경된 기능 → 데이터를 바꾸는 기능(추가·수정·삭제·완료·이동) → 보기만 바꾸는 기능 순으로 돈다.

## 2. 기능마다 이렇게 확인한다

모든 데이터 변경은 `[QA]` 일정에만 한다.

### 정상 동작
기능을 의도대로 한 번 쓰고, 결과를 세 곳에서 확인한다.
- 화면
- 토스트
- 새로고침 후 서버 상태

### 엣지 케이스
기능 지도의 각 기능에 아래 유형을 대입한다. 해당 없는 유형은 건너뛴다.

- **경계값:** 빈 값, 아주 긴 값, 0과 최댓값. 날짜·시간이면 자정, 월말, 주 경계, 연말, 2월 29일, 31일.
- **모순된 입력:** 끝이 시작보다 빠름, 서로 배타적인 옵션을 동시에 켬, 켰다가 끄면 원래 값이 돌아오는지.
- **반복·주기:** 반복 규칙이 있는 기능이면 존재하지 않는 날짜(매월 31일), 일부만 수정·삭제, 반복 전체에 대한 실행 취소.
- **순서 꼬임:** 버튼 연타, 진행 중인 작업(토스트·모달·로딩)이 끝나기 전에 다른 조작, 열린 팝업 위에서 다른 팝업 열기.
- **되돌리기:** 실행 취소, 취소 버튼, 바깥 클릭으로 닫기. 되돌린 뒤 새로고침해도 원래대로인지.
- **양:** 같은 날·같은 시간에 데이터가 많을 때, 목록이 넘칠 때의 표시.
- **입력 필드:** 입력칸이 있으면 한/영 전환, 자모 단위 Backspace, Delete, 선택 영역 덮어쓰기, Ctrl+A, 붙여넣기.
- **상태 유지:** 새로고침, 보기 전환, 다른 화면에 갔다 왔을 때 값과 설정이 남는지.

실제 입력 경로에 달린 것(포커스 상태별 클릭, 호버 잔류, `disable-click` 재적용)은 CDP로 판단할 수 없다. 여기서 다루지 않고 `qa-platform`에 맡긴다.

## 3. 매번 같이 확인할 것

- **콘솔:**
  - 조작 전후로 `browser_console_messages(level: "warning")`을 확인한다.
  - 새 에러나 경고가 나오면 어떤 조작에서 나왔는지 기록한다.
  - Electron CSP 보안 경고처럼 dev 모드에서만 뜨는 경고는 구분한다.
- **접근성 트리:**
  - `browser_snapshot`에서 이름 없는 `button`, 역할 없는 클릭 요소를 기록한다.
- **플랫폼 제약 위반:**
  - 화면에서 `CLAUDE.md` 제약에 기대는 UI가 보이면 기록한다. 예: 스크롤해야만 보이는 내용, 누른 채 끌어야만 되는 조작, 깨진 이미지 자리.

## 4. 재현 정보

버그를 찾으면 코드를 보지 말고, 아래를 채운 뒤 다음 시나리오로 넘어간다. 원인 추적은 리포트를 받은 쪽에서 버그별로 따로 한다.

- **재현 경로:** 다른 사람이 따라 할 수 있게 구체적으로 쓴다(어느 셀, 어떤 키, 어떤 입력값, 어떤 순서).
- **재현율:** 몇 번 시도해 몇 번 재현됐는지. 한 번만 관찰됐으면 "(1회 관찰)"을 붙인다.
- **콘솔:** 그 조작 직후의 에러·경고 원문.
- **스크린샷:** `.playwright-mcp/`의 파일명.
- **서버 상태:** 새로고침한 뒤에도 같은지, 화면에서만 그런지.

## 5. 결과 작성 방식

- **저장 위치:** `.claude/qa/common.md`의 "보고" 섹션을 따른다.
- **섹션 순서:** 요약 표 → 방법 → 정상 동작 → 🔴 높음 → 🟡 중간 → 🟢 낮음 → 기타. 심각도 기준, 제목 형식, 리포트 뼈대는 `common.md`의 "보고" 섹션을 그대로 따른다.
  - **방법:** 앱 버전, 기능 지도(지난 리포트 대비 변화 표시), 참고한 최근 커밋, 테스트 데이터, CDP 한계
  - **정상 동작:** 확인된 기능을 한 줄씩
  - **심각도 섹션:** 각 문제는 기대/실제 → 4번 재현 정보. `[UX]` 문제(동작은 하지만 혼란을 주는 것)는 짧게 쓰고 깊은 평가는 `qa-ux`로 넘긴다.
  - **기타:** 분석, 개발 환경 등
